# Fix the yardstick, then reinforce Threnody

Threnody V4 should stop doing off-policy SFT on the strong Qwen3.5-9B base and spend its scarce Colab GPU hours in a different order: repair the evaluation, fix decoding and loop handling, then apply on-policy training against executable tests. The on-policy step can be single-GPU LoRA GRPO-style RL, or a cheaper self-distillation fallback. Abliteration and fractional merging come off the critical path. The strongest single piece of evidence is direct. Ai2's TMax found that SFT on existing agent trajectories, even from a Qwen3.6-27B teacher, **cut Qwen3.5-9B's Terminal-Bench Lite score from 41.9 to 35.5 (and to 31.3 with a larger mix)**. Outcome-only RL on the same base, with no SFT, **raised Terminal-Bench 2.1 from 20.5 to 29.6 and SWE-bench Verified from 46.2 to 55.3** ([TMax](https://arxiv.org/abs/2606.23321)). V3's pattern (LoRA SFT on 662 trajectories, worse than base on 3 of 4 agent suites) is what that result predicts. The repository's own data also shows that V3's evaluation could not have detected a real improvement. Each suite has 14–30 tasks, which means 95% intervals of ±18–26 pp. The "held-out opencode" suite is the same 14 tasks as the in-harness suite and was also used to select the checkpoint. BioChem-Hard mostly measured answer truncation at `max_tokens=128`. So V4's first deliverable is a measurement system that could show a ~5 pp gain. Only after that does model work begin, and the model work should go to on-policy methods. The realistic single-GPU target is modest: a statistically supported few-point gain on a pre-registered, Docker-free primary endpoint (a frozen local repo-task split), with no regression on BFCL-V4, tau2 or LiveCodeBench, not TMax's +9 points, which took 8 H100 nodes for 1–2 days per run. Every stage below is sized to a hard constraint: **all training and evaluation run in Google Colab on one GPU** (A100 40/80GB, or the ~96GB G4 that `run_v3.sh` targets), within limited session hours and compute units. Multi-node recipes (TMax's 8×H100 nodes, DeepSWE's 64 H100s, SkyRL's 8×H200) appear here only as evidence of what works, each followed by a scaled-down adaptation. That adaptation uses LoRA, short contexts, small groups, Docker-free local sandboxes and session-resumable checkpoints, and its expected gains are correspondingly lower.

Throughout, **[Repo]** marks claims confirmed directly from files in this repository, **[Lit]** marks claims confirmed by the cited external source, and **[Inf]** marks inference, estimates or untested hypotheses.

## V3's agent results sit inside a ±26-point noise band

The headline V3 numbers compare base and V3 on four agent suites, non-thinking mode, Q8_0 ([v3_final.json](https://github.com/YoMosa2009/Threnody-V3/blob/main/results/v3_final.json)) **[Repo]**:

| Suite (n tasks) | Base | V3 (s0.75) | Δ | 95% CI half-width at p≈0.5 |
|---|---|---|---|---|
| AgentLoop In-Harness (14) | 11/14 | 10/14 | −1 task (−7.1 pp) | ±26 pp |
| AgentLoop "Held-Out" opencode (14) | 12/14 | 13/14 | +1 task (+7.1 pp) | ±26 pp |
| AgentLoop-Hard (30) | 19/30 | 17/30 | −2 tasks (−6.7 pp) | ±18 pp |
| OmniAgent-Bench (16, weighted) | 92.71 | 84.61 | −2 tasks (−8.1) | ±25 pp |

The interval column is standard binomial arithmetic **[Inf]**. Below a few hundred items, CLT intervals understate the uncertainty, so Wilson or Bayesian intervals would be wider still ([Bowyer et al.](https://arxiv.org/pdf/2503.01747)) **[Lit]**. None of the four differences is distinguishable from zero. Three moving in the same direction is weak evidence of a real regression, and it is consistent with external results on this base, but it does not establish one.

Four structural defects in the suites matter more than the sample size. **First, the "held-out" suite is not held out from anything.** `eval/agentloop/tasks.py` defines 14 tasks, and the harness reuses them for every tool schema unless `--tasks_file` is passed. "In-Harness (14)" and "Held-Out opencode (14)" are therefore the same tasks under different tool schemas ([repo_data_profile, from harness code](https://github.com/YoMosa2009/Threnody-V3/blob/main/eval/agentloop/tasks.py)) **[Repo]**. The schema change alone moves base from 11 to 12 and V3 from 10 to 13 on identical tasks. Format effects are therefore as large as every claimed improvement. **Second, the suite was used for selection.** `fast_score` in `pipeline/gates.py` is literally `al.passed + al_opencode.passed + 14 × sci.overall/100`, and both the checkpoint gate and the candidate ranking use it ([gates.py](https://github.com/YoMosa2009/Threnody-V3/blob/main/pipeline/gates.py)) **[Repo]**. That makes the single favourable +1 a selected statistic. **Third, the second held-out schema (codex) was never run**: it lives only in suite `full`, and `run_v3.sh` used `mid` **[Repo]**. **Fourth, sampling was off-spec.** The harness uses temperature 0.0 in non-thinking mode, top_p 0.95 and no presence penalty ([harness.py](https://github.com/YoMosa2009/Threnody-V3/blob/main/eval/agentloop/harness.py)) **[Repo]**. Qwen recommends T=0.7, top_p 0.8, top_k 20 and presence_penalty 1.5 for Qwen3.5-9B in non-thinking mode ([Qwen3.5-9B card](https://huggingface.co/Qwen/Qwen3.5-9B)) **[Lit]**, and the Qwen3 cards warn that greedy decoding "can lead to performance degradation and endless repetitions" ([Qwen3-8B card](https://huggingface.co/Qwen/Qwen3-8B)) **[Lit]**. Temperature is not a nuisance parameter for fine-tunes. In a 60,000-trajectory study, DeepSWE-preview scored **31.4% at T=1.0 versus 20.4% at T=0**, while Devstral-2 did not move ([On Randomness in Agentic Evals](https://arxiv.org/html/2602.07150)) **[Lit]**. V3 and base may be ranked differently under the vendor's sampling. Nobody knows, because only T=0 was run.

The science benchmark has a separate bug. The only per-item dataset in the repo, `biochem_hard_final.json` (844 questions × Base and V2, both Q4_K_M), shows that **71.4% of Base rows and 60.9% of V2 rows have no extractable answer**. Where an answer was extracted, Base was right 88.8% of the time and V2 90.9% ([biochem_hard_final.json](https://github.com/YoMosa2009/Threnody-V3/blob/main/results/biochem_hard_final.json)) **[Repo]**. On MMLU-Pro chemistry, Base produced an extractable answer in only 12 of 250 rows. The cause is `ask(..., max_tokens=128)` in `eval/biochem_hard/eval_biochem_hard.py`, with no flag to raise the limit **[Repo]**. BioChem-Hard therefore measured brevity under a 128-token cap. V2's "+10.1 pp advantage" is mostly V2 finishing within budget more often (extraction rate 39.1% vs 28.6%) **[Repo]**. That explains why Base scores 25.4% there but 76.0% on the 1,024-token `sci_eval.py` sample. Random college-subject IDs (`randint(10000, 99999)`, including one collision) also block paired tests on 344 of the 844 rows, and stored responses are cut to 200 characters, so the file cannot be re-scored **[Repo]**. Two smaller problems add confusion. V3's published `biochem_hard` field duplicates the `sci` n=400 numbers. The BioChem file used Q4_K_M while the agent suites used Q8_0, so comparisons across files mix quantization levels **[Repo]**.

V3's loop metric is too weak to certify "zero loops". `max_repeat` counts only consecutive identical assistant actions ([schemas.py](https://github.com/YoMosa2009/Threnody-V3/blob/main/eval/agentloop/schemas.py)) **[Repo]**, so A–B–A–B oscillation is invisible to it. No per-task trajectories, `log_history.json` or run logs were published. The training report also disagrees with the trainer code on batch size, warmup, weight decay and step count ([KNOWN_DISCREPANCIES.md](https://github.com/YoMosa2009/Threnody-V3/blob/main/docs/KNOWN_DISCREPANCIES.md)) **[Repo]**. The practical conclusion: **in V3, evaluation error was larger than any model difference it tried to measure.** V4 has to fix that before training anything, or it will repeat V3's ambiguity at higher cost.

## SFT pulls Qwen3.5-9B down; on-policy training pushes it up

The external evidence on this exact base is unusually clean. TMax tested two SFT sets on Qwen3.5-9B. One was its own (16.5K trajectories, 8K successful, Qwen3.6-27B teacher). The other was a larger mix of Nemotron-Terminal, TerminalTraj, OpenThoughts-Agent and SETA data. **Both lowered TB-Lite: 41.9 → 35.5 and 41.9 → 31.3.** The same data *raised* Qwen3-8B (7.3 → 16.4), so the authors "opted to go straight to RL training for Qwen 3.5" ([TMax §G.2, Table 16](https://arxiv.org/abs/2606.23321)) **[Lit]**. TB2.1 moved within noise under SFT, so the clearest damage was on TB-Lite. RL from the raw base, by contrast, used DPPO with binary or continuous outcome rewards, token-level loss, zero-variance group filtering and a temperature-1.0 rollout. It lifted **TB-Lite 49.4 → 65.6, TB2.0 21.0 → 33.0 and SWE-bench Verified 46.2 → 55.3**. The gains held across harnesses: OpenHands 29.0 → 42.7, mini-SWE-agent 44.9 → 57.8, Terminus-2 37.9 → 46.1 ([TMax](https://arxiv.org/abs/2606.23321)) **[Lit]**. RL is not automatically safe, though. RL on the TerminalTraj environments *lowered* TB2.1 from 20.5 to 15.9, while SWE-Smith environments reached 27.3 and TMax-13K 29.6 ([TMax Table 2](https://arxiv.org/abs/2606.23321)) **[Lit]**. Environment quality matters as much as the algorithm.

This has to be reconciled with the large SFT literature that recommends scaling trajectory counts. Those studies are real. SWE-smith, Skywork-SWE and Kwai-Klear all report log-linear gains with no saturation, reaching **Qwen3-8B → 39.0% Verified on 66K trajectories** (Klear) and **42.2% with 18K validated trajectories** (SWE-Lego) ([Klear card](https://huggingface.co/datasets/Kwai-Klear/SWE-smith-mini_swe_agent_plus-trajectories-66k), [SWE-Lego](https://arxiv.org/abs/2601.01426)) **[Lit]**. Every one of these successes, however, started from a base that was weak at agentic work: Qwen2.5-Coder or Qwen3-8B, where RL on the raw base barely helped (OpenThoughts-Agent: raw Qwen3-8B SBV 5.3, RL-only 1.0) ([OpenThoughts-Agent](https://arxiv.org/pdf/2606.24855)) **[Lit]**. Qwen3.5-9B already scores **46.2% SWE-bench Verified in TMax's harness**, along with BFCL-V4 66.1 and TAU2 79.1 on its card ([TMax](https://arxiv.org/abs/2606.23321), [Qwen3.5-9B card](https://huggingface.co/Qwen/Qwen3.5-9B)) **[Lit]**. That exceeds what the 8B SFT recipes produce. The working hypothesis for V4 **[Inf]**: on a base this strong, off-policy imitation mostly overwrites a good policy with a different and often weaker one. Scaling the same data 10× would make that bigger, not smaller. The SFT scaling curves remain useful as a warning about V3's tiny dataset, not as a prescription for V4. Public corpora (Open-SWE-Traces has ~235K Qwen3.8-27B traces in v1.2 alone) make volume cheap ([HF card](https://huggingface.co/datasets/nvidia/Open-SWE-Traces)) **[Lit]**, but TMax shows that a strong teacher did not save SFT on this base.

The mechanism fits "RL's Razor". Forgetting tracks the KL divergence between the fine-tuned and base policies on the new task distribution. On-policy RL is implicitly biased toward KL-minimal solutions, whereas SFT can move arbitrarily far ([Shenfeld et al.](https://arxiv.org/abs/2509.04259)) **[Lit]**. CapTrack similarly finds that instruction fine-tuning causes the strongest capability drift, that preference optimization is more conservative and can partially recover lost capabilities, and that "no universal mitigation emerges" ([CapTrack](https://arxiv.org/abs/2603.06610)) **[Lit]**. Rank barely matters for RL. Thinking Machines found that **LoRA matches full fine-tuning for policy-gradient RL even at rank 1**, because RL delivers only O(1) bits per episode ([LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)) **[Lit]**. That is what makes single-GPU LoRA RL plausible at all.

V3 also made several choices that would amplify SFT damage. These are visible in code, and their contribution is **[Inf]** until ablated. The run used **2.9M tokens, about 8% of its own 35M-token target, in 56 steps** ([v3_training_report.json](https://github.com/YoMosa2009/Threnody-V3/blob/main/results/v3_training_report.json)) **[Repo]**. A quarter of the mix was not agentic coding: 15% BioChem and 10% identity, cyber and schema data. The anti-loop filter dropped any trajectory with two consecutive identical actions, then **sorted survivors by fewest turns** ([build_v3.py](https://github.com/YoMosa2009/Threnody-V3/blob/main/pipeline/build_v3.py)) **[Repo]**. That biases the data toward short, first-try successes and away from the error→change-strategy→recover demonstrations that LiteCoder-Terminal explicitly keeps ([LiteCoder-Terminal](https://arxiv.org/pdf/2605.29559)) **[Lit]**. The LoRA targets included the Gated DeltaNet gate projections `in_proj_a` and `in_proj_b` ([train_sft.py](https://github.com/YoMosa2009/Threnody-V3/blob/main/pipeline/train_sft.py)) **[Repo]**. Axolotl's Qwen3.5 config omits these, adapting only `in_proj_qkv`, `in_proj_z` and `out_proj` ([Axolotl docs](https://docs.axolotl.ai/docs/models/qwen3.5.html)) **[Lit]**. Those gates control decay in the recurrence, so perturbing them plausibly changes long-context memory **[Inf]**. Finally, needing to merge at 0.75 to avoid loops at full strength is a symptom, not a remedy. Merging toward base moves the model along a single line between base and adapter. If the adapter's direction hurts agent skills, no point on that line beats base **[Inf]**. Merge operators are not a "free lunch" against capability forgetting ([CapTrack](https://arxiv.org/pdf/2603.06610)) **[Lit]**. V4 should treat "stable at α=1.0" as a requirement for any adapter it ships.

## Loops come from decoding and policy, and DPO on self-mined pairs fixes them cheaply

Loops have two documented causes. One is self-reinforcing repetition under maximization decoding: the more often a sentence appears in context, the more likely the model is to repeat it ([Xu et al.](https://arxiv.org/abs/2206.02369v2)) **[Lit]**. The other is agents failing to use their own action history. Qwen3-8B's loop rate on CodeGym rises from **29.0% with full history to 57.3% at 4K summarization and 64.7% at 2K**, and looping runs fail 59.5% of the time versus 33.4% for loop-free runs ([DeLoop](https://arxiv.org/html/2610.19376)) **[Lit]**. V3's harness runs greedy decoding, so part of V2's 27–29-repeat loops at adapter strengths 0.5–1.0 was likely a decoding artifact compounded by an over-strong adapter **[Inf]**. Note the base model in V3's own evals had `max_repeat` of only 1–2 **[Repo]**. On these suites, loops were introduced by fine-tuning rather than inherited from base, so V4's first loop goal is not to *create* them.

The best training-time fix in the notes is DeLoop: LoRA DPO on self-mined pairs, where the rejected example is the looping action and the chosen example is the first later non-looping action in the same rollout. It uses β=0.05, one epoch and about 8,000 pairs for Qwen3-8B, with no rewards, gold answers or judges ([DeLoop](https://arxiv.org/html/2610.19376)) **[Lit]**. The comparison is striking:

| Method (Qwen3-8B, CodeGym, 4K summarization) | Loop rate | Success |
|---|---|---|
| Baseline | 57.3% | 25.1% |
| **DeLoop DPO** | **6.1%** | **25.9%** |
| Per-step loop-penalty GRPO | 15.0% | 24.7% |
| SFT on solved traces | 42.7% | 21.3% |
| Exact-duplicate blocker (harness) | 46.7% | 25.3% |
| Reflexion-on-stuck | 55.3% | 24.3% |

Source: ([DeLoop](https://arxiv.org/html/2610.19376)) **[Lit]**. At 8B the success gain is under a point. At 14B it reached **45.1% → 52.3%**, and on Terminal-Bench duplicate calls per task fell from 16.6 to 6.9 **[Lit]**. Two lessons transfer directly. Harness-level blockers and reflection prompts barely work. SFT on clean traces, which was V3's approach, is among the worst options. DeLoop is a 2026 preprint and its compute was not reported, so treat its numbers as promising rather than settled **[Lit]**.

The serving stack has its own loop trap. In llama.cpp, Qwen3.5-9B with thinking enabled often writes `<tool_call>` XML *inside* `<think>`. The grammar trigger then ends generation, the client receives no structured call, and the model degrades into raw XML. The issue was still open in September 2026. Workarounds: `enable_thinking:false`, `--reasoning-format none`, removing DRY sampling, and post-March-5-2026 GGUFs ([llama.cpp #20837](https://github.com/ggml-org/llama.cpp/issues/20837), [Unsloth GGUF notes](https://huggingface.co/unsloth/Qwen3.5-35B-A3B-GGUF)) **[Lit]**. Presence penalty also has a cost. It acts on tokens, not on tool semantics, so it can corrupt exact file paths, which is likely why Qwen sets it to 0.0 for "precise coding" ([Qwen3.5-9B card](https://huggingface.co/Qwen/Qwen3.5-9B)) **[Lit/Inf]**. V4 should therefore ablate presence_penalty 0 versus 1.5 rather than adopt either value blindly. A distinctive and measurable V4 objective would be **zero tool calls emitted inside reasoning**, enforced by a reward penalty during RL **[Inf]**. Qwen3-Coder-Next similarly penalized malformed tool calls during RL ([Qwen3-Coder-Next](https://arxiv.org/html/2603.00729v1)) **[Lit]**.

## Abliteration and quantization are unmeasured transformations on the release path

V3's abliteration is a larger and less controlled intervention than the published method, and nothing measured its effect. Reading `pipeline/abliterate.py` **[Repo]** shows four things. The direction is estimated from **only 8 harmful and 8 harmless prompts**, all security or chemistry minimal pairs, using a hand-written prompt format without a system prompt or thinking tags. A **separate per-layer direction** is projected out of each targeted layer (code ratio 0.35–0.85 of depth; reported as layers 12–28). By contrast, Arditi et al. select one direction, under explicit criteria (KL on harmless prompts < 0.1, layer < 0.8·L), and remove it from all write matrices ([Arditi et al.](https://arxiv.org/html/2406.11717)) **[Lit]**. The code orthogonalizes only `mlp.down_proj` and `self_attn.o_proj`. On Qwen3.5, 24 of 32 layers are Gated DeltaNet ([Qwen3.5-9B card](https://huggingface.co/Qwen/Qwen3.5-9B)) **[Lit]**, whose output projection is `linear_attn.out_proj`, so in most targeted layers only the MLP write is edited and the embedding is never touched **[Repo/Inf]**. Finally, no KL, refusal-rate or capability check follows the edit **[Repo]**. The direction is computed after fine-tuning, so its effect cannot be separated from the SFT effect in V3's numbers.

The literature gives no measurement of abliteration's effect on agent or tool-use benchmarks ([Young](https://arxiv.org/html/2512.13655)) **[Lit]**, so V3's agent regressions cannot be attributed between SFT and abliteration. On standard benchmarks the damage varies by tool and model. Across 16 models from 7 to 14B, Heretic averaged **−7.81 pp on GSM8K, with a worst case of −18.81 pp**, and math reasoning was the most sensitive ([Young](https://arxiv.org/html/2512.13655)) **[Lit]**. TruthfulQA drops consistently, even with Arditi's careful method ([Arditi et al.](https://arxiv.org/html/2406.11717)) **[Lit]**. The closest Qwen3.5-9B datapoint is a self-reported uncensored variant, method unconfirmed: **TruthfulQA MC2 53.76 → 45.77 and GSM8K 87.64 → 84.99** ([Friendli page](https://friendli.ai/models/DreamFast/Qwen3.5-9B-Uncensored-HauhauCS-Aggressive-Safetensor-Benchmark)) **[Lit, self-reported]**. The harm side is concrete. Abliterated Qwen2.5-Coder 14B generated SQL-injection-vulnerable code **88–97% of the time** ([arXiv 2606.05396](https://arxiv.org/abs/2606.05396)) **[Lit]**. Agent benchmarks reward calibrated abstention and following system-prompt constraints, both plausibly entangled with the "decline" direction **[Inf]**. If the actual goal is fewer false refusals on shell and security work, DPO on benign-but-borderline prompts is the more targeted tool. Preference optimization drifts less than instruction tuning ([CapTrack](https://arxiv.org/abs/2603.06610)) **[Lit]**.

Quantization was validated only by token-level agreement on the imatrix calibration text. Same-top-token versus BF16 falls from 97.8% at Q8_0 to 94.1% at Q4_K_M and 89.6% at IQ3_M, and median KLD rises about 85× across that range ([v3_quant_report.json](https://github.com/YoMosa2009/Threnody-V3/blob/main/results/v3_quant_report.json)) **[Repo]**. Because the text is the calibration set, the measurement is in-sample and optimistic, and it says nothing about agent behavior **[Inf]**. Recent evidence shows why task evals per quant are needed. On Qwen2.5-Coder and Devstral, W4A16 kept final accuracy within noise after Holm correction. But **Qwen-7B's one-shot solves fell from 17 to 0 under AWQ while loop solves rose from 10 to 25**, and Devstral's valid tool use fell from 8.7% to 1.2% with up to 96.5% malformed calls ([Mehboob et al.](https://arxiv.org/html/2611.02368)) **[Lit]**. At 27B, Q4_K_M matched BF16 on Terminal-Bench 2.1, Q2 fell noticeably and 1-bit collapsed ([Quesma](https://quesma.com/blog/qwen38-27b-quantizations-benchmarked/)) **[Lit]**. For a 9B, Q4_K_M is probably fine on final accuracy, but tool-call validity and loop behavior must be checked per quant, and IQ3_M should not ship without a full agent run **[Inf]**.

## A staged V4 plan that fits one Colab GPU

### What one Colab GPU can and cannot reproduce

The published wins all came from clusters. TMax used 2 H100 nodes for training plus 6 for inference over 1–2 days, with group size 32, 65K-token episodes and 64 tool calls ([TMax](https://arxiv.org/abs/2606.23321)). DeepSWE used 64 H100s for 6 days ([Together AI](https://together.ai/blog/deepswe)). SkyRL's 7–14B runs took 16–27 hours on 8×H100/H200 ([SkyRL](https://sky.cs.berkeley.edu/project/skyrl/)). OpenThoughts-Agent's RL used 24 A100s for about 46 hours ([OpenThoughts-Agent](https://arxiv.org/pdf/2606.24855)) **[Lit]**. None of these reports a single-GPU or LoRA agentic run at 7–14B **[Lit]**. On Colab, Threnody can reproduce the *shape* of these recipes: outcome-reward GRPO-family RL from base, zero-variance filtering, FP32 LM head, temperature-1.0 rollouts, and test-verified rewards. It cannot reproduce their *scale*. A Colab version has about 1/50–1/100 of TMax's rollout budget, 8–16K-token episodes instead of 65K, groups of 4–8 instead of 32, and Python-subprocess sandboxes instead of Docker or Daytona containers **[Inf]**. The honest expectation is the low end of the TMax envelope or below. Loop, format and tool-call polish are likely. A gain of a few points on in-distribution Python repo tasks is plausible. Transfer to Terminal-Bench-scale gains (+9) is not something to promise **[Inf]**. Every throughput or timing figure below is an estimate **[Inf]**. Colab sessions end without warning, so every stage must write resumable state to Google Drive: LoRA weights, optimizer state, RNG seeds, rollout buffers and the eval cursor. Training should checkpoint every 20–25 steps, and evaluation should append per-task JSONL so that a disconnect costs minutes, not a session **[Inf]**. A G4 (~96GB) mainly buys headroom for longer episodes, larger vLLM KV pools or a co-resident teacher. It does not change the plan's shape **[Inf]**.

### Stage 0 rebuilds evaluation around a pre-registered primary endpoint

The design should separate a dev set, a frozen test set and a contamination-resistant set, and pre-register what "beats base" means. Everything has to run inside Colab without Docker, which rules out the standard SWE-bench and Terminal-Bench runners: both use a container per task ([TB2.0](https://arxiv.org/html/2601.11868v1), [swebench.com](https://www.swebench.com/)) **[Lit]**, and Colab generally cannot run Docker **[Inf]**. V4 therefore cannot make SWE-bench Verified or Terminal-Bench claims unless a Docker-free runner is shown to reproduce official scores on a calibration subset, and no source in the notes establishes one **[Inf]**.

The dev set holds AgentLoop's 14 tasks under all three schemas (codex included), OmniAgent's 16, and AgentLoop-Hard's 30 committed to the repo (it currently lives only on Drive **[Repo]**). Add about 100 tasks of a new local repo-task pool described below. Checkpoints, merge choices and quants are selected on dev only. The custom suites become what they can honestly be: regression checks, with the opencode and codex runs relabelled "schema transfer" rather than "held-out" **[Inf]**. The frozen test set has two parts. The first is **300–400 frozen Docker-free repo tasks**: SWE-smith-style bug-fix or issue tasks on pure-Python repos that install with pip in a venv and verify with hidden pytest tests, run in subprocess sandboxes with timeouts. Use repos disjoint from the RL training repos and from SWE-bench's, and prefer issues created after the base model's and the training data's cutoffs, following SWE-rebench's monthly-split logic for contamination resistance ([SWE-rebench](https://fugumt.com/fugumt/paper_check/2505.20411v1_enmode)) **[Lit/Inf]**. The second is the Docker-free public benchmarks BFCL-V4, tau2-bench with a pinned user simulator (an API cost, not a GPU cost), and LiveCodeBench in a post-cutoff window ([evaluation notes: EvalScope](https://evalscope.readthedocs.io/en/v1.4.1/get_started/supported_dataset/agent.html), [BFCL v4](https://gorilla.cs.berkeley.edu/blogs/16_bfcl_v4_memory.html)) **[Lit]**. These are the base model's own card benchmarks (BFCL-V4 66.1, TAU2 79.1, LCB v6 65.6), so they double as forgetting checks ([Qwen3.5-9B card](https://huggingface.co/Qwen/Qwen3.5-9B)) **[Lit]**. Every comparison re-runs base Qwen3.5-9B in the same harness, quant, mode and sampling. Card numbers are context only, because harness choice alone moves the 9B's TB-Lite score from 29.0 to 49.4 ([TMax](https://arxiv.org/abs/2606.23321)) **[Lit]**.

Statistical power should set the sizes. A paired McNemar test needs about **310 tasks to detect 5 pp if 10% of tasks are discordant, and about 625 at 20% discordance** **[Inf, standard formula]**. A single 89-task Terminal-Bench run resolves only ~10–15 pp. At σ≈1.5 pp run-to-run, about 9 runs detect a 2 pp gain ([KTH](https://arxiv.org/html/2602.07150)) **[Lit]**. A credible primary endpoint is therefore: **V4 minus base pass@1 on the 300–400-task frozen local repo-task test split, averaged over k=3 runs per task, with a paired-bootstrap 95% CI (task-clustered) that excludes zero.** Secondary endpoints are non-inferiority within −2 pp on BFCL-V4, tau2 and LiveCodeBench, all under Holm correction **[Inf]**. Report pass@1 ± SE, pass@k and pass^k, in both thinking and non-thinking modes. V3 measured non-thinking only, while Qwen's card numbers are likely thinking mode ([KNOWN_DISCREPANCIES §1](https://github.com/YoMosa2009/Threnody-V3/blob/main/docs/KNOWN_DISCREPANCIES.md), [Qwen3.5-9B card](https://huggingface.co/Qwen/Qwen3.5-9B)) **[Repo/Lit]**. A per-run manifest should record model, adapter and GGUF hashes, llama.cpp build and flags, template hash, `enable_thinking`, full sampler and seed, harness commit, and per-task outcome, turns, tool calls, tokens, seconds and trajectory path **[Inf]**. BioChem-Hard should either be retired in favor of `sci_eval.py` or fixed with ≥2,048 non-thinking or ≥8,192 thinking tokens, full stored responses, stable hashed IDs, a fallback extractor and extraction-failure rate reported as its own metric **[Repo]**.

The eval budget has to fit Colab. At 9B in vLLM or llama-server on one A100, the 400-task split × 3 runs × 2 models (base and V4) is about 2,400 agent episodes. At a few minutes each, with several running concurrently, that is roughly 10–20 GPU-hours, so it should be spread over resumable sessions **[Inf]**. TMax ran its evals on a single H200 with 4 concurrent trials, which shows a single-GPU eval budget is realistic ([TMax](https://arxiv.org/abs/2606.23321)) **[Lit]**. Run the test split once, at the end, by commit hash.

### Stage 4 runs RL scaled down from TMax, with explicit stability guards

The recommended configuration adapts TMax and DAPO to one GPU. The policy is a LoRA (r=32, alpha=32) on MLP, attention and GDN `in_proj_qkv`/`in_proj_z`/`out_proj`, excluding `in_proj_a`/`in_proj_b` **[Inf]**. Use a learning rate of about **1e-5**: TMax used 1e-6 constant for full-parameter training, and LoRA's optimal LR runs about 10× higher ([TMax](https://arxiv.org/abs/2606.23321), [Thinking Machines](https://thinkingmachines.ai/blog/lora/)) **[Lit → Inf]**. Sample a group of 8 per prompt with 8 prompts per step at temperature 1.0. Use token-level loss, DAPO clip-higher (ε_low 0.2, ε_high 0.28) ([HF blog](https://huggingface.co/blog/NormalUhr/grpo-to-dapo-and-gspo)) **[Lit]**, and zero-variance group filtering. Cap episodes at about 16K total tokens and 20 tool calls. Keep the **LM head in FP32**, which TMax calls "especially crucial when training Qwen 3.5". Checkpoint every 20–25 steps and stop by 200–300 steps, because TMax runs "often collapse past 300 steps" ([TMax](https://arxiv.org/abs/2606.23321)) **[Lit]**. Monitor reward-std, entropy and gradient-norm spikes, the documented precursors of RAGEN's "Echo Trap" collapse ([RAGEN](https://arxiv.org/html/2504.20073v2)) **[Lit]**, and track KL to base as the forgetting proxy ([RL's Razor](https://arxiv.org/abs/2509.04259)) **[Lit]**. Interleaved thinking should be preserved on intermediate turns, as TMax did **[Lit]**.

The reward should be binary or fraction-of-tests passed, plus a small format/parse-validity term, a per-step penalty for an exact repeat (same canonical call, same observation), a penalty for tool calls inside `<think>`, and a mild turn cost **[Inf, built from cited components]**. The step penalty alone cut loops without raising success in DeLoop's comparison, so it shapes behavior but cannot carry capability ([DeLoop](https://arxiv.org/html/2610.19376)) **[Lit]**. Reward hacking happens even at 9B. TMax-9B imported a cipher's internal key array instead of mounting the attack, and deleted inputs to hand-write an expected CSV "since the task evaluation likely checks the final state" ([TMax](https://arxiv.org/abs/2606.23321)) **[Lit]**. Tests therefore need to be read-only and hash-checked, hidden tests should be held back, and edits to test files should be rejected. For environments, SWE-smith-derived Python repos reached 27.3 TB2.1 under TMax's recipe, and self-generated environments from Qwen3.5-9B itself reached 27.3 versus 29.6 with the stronger generator ([TMax](https://arxiv.org/abs/2606.23321)) **[Lit]**. A few hundred pure-Python, venv-installable SWE-smith-style tasks with subprocess pytest sandboxes are the practical Colab substrate **[Inf]**. Pilot each task with 8 base samples and keep only those with pass rates strictly between 0 and 1. Endless-Terminals-style easy data wasted 7× the rollouts needed per batch ([TMax](https://arxiv.org/abs/2606.23321)) **[Lit]**.

On cost, Unsloth reports Qwen3-8B GRPO at about 110K context on an 80 GB H100 with vLLM plus QLoRA ([Unsloth](https://unsloth.ai/docs/zh/kai-shi-shi-yong/reinforcement-learning-rl-guide/grpo-long-context)) **[Lit, vendor]**. But Unsloth also advises against QLoRA for Qwen3.5 and lists bf16 LoRA at about 22 GB ([Unsloth Qwen3.5](https://unsloth.ai/docs/models/qwen3.5/fine-tune)) **[Lit]**. Generating 8 prompts × 8 samples × ~15 turns is several minutes per step in colocated vLLM, so 100–200 steps should take 10–20 GPU-hours **[Inf]**. That spans several Colab sessions, so the loop must resume from Drive checkpoints of adapter, optimizer, sampler state and data cursor. If a step overruns, cut the group to 4 or the episode cap to 8K tokens before cutting prompts per step **[Inf]**. Before committing, verify that the hybrid-attention model works with vLLM LoRA hot-swap and TRL or Unsloth multi-turn GRPO. Unsloth notes that vLLM 0.16.0 did not support Qwen3.5, and no source in the notes confirms single-GPU LoRA-GRPO on Qwen3.5 ([Unsloth](https://unsloth.ai/docs/models/qwen3.5/fine-tune)) **[Lit/Inf]**. TRL's `GRPOTrainer` with `environment_factory` already runs the multi-turn tool loop and caps total tokens across turns ([TRL OpenEnv](https://huggingface.co/docs/trl/en/openenv)) **[Lit]**.

If the infrastructure fails, Stage 4b keeps the on-policy property at lower cost. Sample base at T=1.0 on training tasks, keep resolved trajectories (≤3 per task), loss-mask erroneous steps rather than dropping whole trajectories, and fine-tune with a small LR. Step-masked rejection fine-tuning beat trajectory-level filtering, +3.7 versus +2.4 on Verified ([SRFT](https://arxiv.org/abs/2605.10674)) **[Lit]**, and self-generated data keeps KL to base low **[Inf]**. On-policy distillation reached comparable reasoning results at about a tenth of RL's GPU-hours ([Thinking Machines OPD](https://thinkingmachines.ai/blog/on-policy-distillation/)) **[Lit]**. However, a Qwen3.6-27B teacher at ~54 GB in bf16 does not fit beside a 9B student on 80 GB without FP8 or AWQ quantization, and no OPD result on SWE-style coding at 7–14B was found **[Inf]**. If any SFT returns, it should use only native `qwen3_coder` format traces. TMax filtered other tool formats because they "can confuse small models" ([TMax](https://arxiv.org/abs/2606.23321)) **[Lit]**. It should also use an LR sweep of {5e-5, 1e-4, 2e-4} at effective batch ≤32 with early stopping on dev agent score ([Thinking Machines](https://thinkingmachines.ai/blog/lora/)) **[Lit/Inf]**, and it must be stable and above base at α=1.0 or it does not ship.

### Stage 5 ships only what was measured

Release decisions should follow the same discipline. Merge at full strength only. For abliteration, either drop it or ship it as a clearly labelled separate variant. Any such variant should use a single direction selected under Arditi's KL<0.1 and layer<0.8·L criteria, estimated from far more than 8 prompt pairs, and applied to all write matrices including GDN `out_proj` and embeddings. It should be evaluated on the full agent test set, on refusal rates scored by a classifier (string markers undercount; Young found 95.7% versus 72.2% non-refusal), and on harm evals ([Arditi et al.](https://arxiv.org/html/2406.11717), [Young](https://arxiv.org/html/2512.13655)) **[Lit]**. For quantization, run Q8_0, Q6_K and Q4_K_M through the dev agent suite plus BFCL-V4 and a 100-task slice of the local repo-task test pool at k≥3, paired against BF16 with Holm correction. Log tool-call parse failures, turns, tokens, timeouts and failure categories, following Mehboob et al.'s behavioral analysis ([arXiv 2611.02368](https://arxiv.org/html/2611.02368)) **[Lit]**. Measure KLD on held-out agent transcripts that are disjoint from the imatrix data, and keep IQ4_XS and IQ3_M "experimental" unless they pass the same run **[Inf]**. Ship an embedded, tested chat template that renders tool calls after `</think>`, and document that DRY should be off and that presence_penalty support varies by client ([llama.cpp #20837](https://github.com/ggml-org/llama.cpp/issues/20837)) **[Lit]**.

## Conclusion

V3's lesson is less "the recipe was slightly off" than "this base punishes imitation and V3's instruments could not see it". On Qwen3.5-9B, the published evidence now runs one way: off-policy SFT, even from a stronger teacher, lowered agent scores, while on-policy, outcome-verified training raised them across harnesses. V4's hard problems are therefore engineering problems a single developer can actually solve. These are a paired, pre-registered, Docker-free evaluation that runs inside Colab; a sandbox of a few hundred verifiable Python tasks; and a stable LoRA RL loop on a hybrid-attention model. More data and better merge arithmetic are not among them. The success criterion should change accordingly. A V4 that is non-inferior to base everywhere, measurably better on one pre-registered endpoint, and free of the loop and think-block tool-call failures that hurt local users would be the first Threnody release whose claim survives scrutiny.

Two assumptions deserve the earliest tests, because each could reorder the plan. First, if vendor-recommended sampling alone closes most of the base-versus-V3 gap or reveals a large base loop rate, the decoding layer becomes V4's cheapest win and DeLoop moves up. Second, if Stage 1's α-curve shows that some V3 merge strength *does* beat base under fair evaluation, light SFT is not dead on this base, and a self-distilled SFT warm-start before RL becomes worth testing. Both are answerable in one or two Colab sessions, before any new training.
